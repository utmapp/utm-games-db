How Auto-Triage works

Game compatibility is a complex issue because graphics drivers often need to include tweaks and workarounds for specific games. The traditional approach is to hire a lot of people to play-test the games to find issues and then hire more people to debug and patch the driver. This is one reason why so few graphics card makers exist: it requires significant capital to maintain these large teams. As a small, open source, project we are changing the script by leveraging the community to test games and new automation technology to fix them. Note that we are not re-compiling, reverse engineering, or remaking any games. The goal is to get games to run as faithfully as possible in UTM. Auto-Triage is an automated agent that takes a compatibility report, reproduces the problem on a real test machine, and tries to fix it in UTM's driver stack.

Requirements

The agent needs a licensed copy of the game to run it. Games that are owned on the triage machines show Auto-Triage available on their page and are picked up automatically. Games that are not owned by any of the triage machines shows Auto-Triage unavailable. You can change that by gifting a copy to one of our storefront accounts or pointing us to a free demo from the game's page; look for the Donate a copy button. This is the second most consequential way of having game compatibility issues resolved (the most consequential is submitting a detailed bug report).

The triage pipeline

Reports move through the stages below. Boxes on the left are the main path; the branches to the right are where a report leaves it. The pill in each box is the status you will see on the report.

Step by step

1. A report is queued Pending

Our test machines are Macs with development and debugging tools installed, each running a copy of the agent. When a report comes in for a game with Auto-Triage available, it joins a queue and waits for a machine whose agent holds a license for that game. Priority is given to games with the most stars. The report shows Pending until one picks it up.

2. The agent reproduces the issue In progress

The agent installs the game on the machine, sets up UTM to match the configuration in your report as closely as it can, and follows your steps to reproduce. This is where a precise report pays off: the UTM version, guest OS, graphics backend, and concrete steps all narrow the search. Private attachments such as logs and recordings are read at this stage too.

3. When it cannot reproduce Needs clarification Cannot reproduce

If the problem does not show up, the agent leaves a comment on the report asking for whatever is missing: a setting it could not infer, a save file, a clearer sequence of steps. The report is marked Needs clarification and goes back into the queue as soon as you reply. If the problem still cannot be triggered after the extra information, or there is nothing more to ask, the report is marked Cannot reproduce. Either way, the comment and status are only posted after the independent check in step 6 confirms that the problem was really looked for, at your settings and in the place you describe. A new report with different details can start the process again.

4. The agent works on a fix In progress

Once the issue reproduces reliably, the agent looks for the cause anywhere in the stack that UTM controls: the guest drivers, the host side, the hypervisor, and the graphics translation layers in between. It compares against the same game in CrossOver to decide which layer is at fault. One report can hide several layered bugs, and fixing the first crash does not finish it: the agent keeps a list of every symptom you describe and keeps working until each one is fixed, or shown to be outside UTM's control. Where a fix needs a design choice, the agent makes it against the documentation and the evidence and explains it, rather than leaving the question to a maintainer. Some problems turn out to be outside that reach, for example a limit of the hardware itself, or is a known architectural issue. In that case the agent explains why and marks the report Not to fix.

5. The fix is validated In progress

A fix that makes one game work is not enough on its own. The agent reruns your steps with every fix applied and checks that each symptom is gone, writes a small test that fails before the fix and passes after where one can show the bug, runs the full regression test matrix on both graphics backends, benchmarks the change against the current build, and runs a code review to find similar issues elsewhere. If any of that fails, it goes back to step 4.

6. An independent check In progress

When the agent believes it is done, its drafted comment and status go to a second, independent agent with a fresh context whose job is to check the report. The checker makes its own list of the symptoms in your report and compares it with the draft and with the evidence the triage left behind: the test runs, screenshots, benchmark results, the fix commits and whether the branches are published. It confirms that every claim in the comment is backed by that evidence, that no symptom you reported is left open, that every validation step was actually run, and that the comment contains no personal data.

If the check passes, the comment and status are posted to your report. If it fails, the report goes back to the same triage agent, with everything it had learned so far, together with a list of what is missing, and the agent continues the work from step 4. The triage agent may overrule a finding when its own evidence shows the finding is wrong, and after three rounds its result is posted as is, so a disagreement cannot hold up a report forever.

7. Pull requests for human review Fix proposed

When the check passes, the report is marked Fix proposed and the agent opens pull requests against the relevant repositories. Maintainers review them and may send them back for more changes. In that case the agent picks the report up again and, once the new work has passed the check, posts a follow-up comment that says why the work continued and what changed; earlier comments stay on the report. Nothing the agent writes reaches a release without a human accepting it.

8. Shipped

Accepted fixes are distributed in a future UTM update or, for driver changes, in a driver update. Once you have updated, a fresh report on the new version is the best way to confirm the fix and to move the game's status.

Helping the agent help you

  • One issue per report. The agent triages each report on its own; a report that mixes several problems is harder to reproduce and to close.
  • Exact versions and settings. UTM version, guest OS, graphics backend, and your Mac's chip are the first things the agent tries to match.
  • Steps, not symptoms. "Crashes in the second level after the cutscene" can be followed; "crashes sometimes" cannot.
  • Attach logs and recordings. Attachments are private to you, the maintainers, and the agent, and are often the fastest route to the cause.
  • Answer clarification requests. A report marked Needs clarification is paused until you reply.
  • Donate a copy. If a game shows Auto-Triage unavailable, gifting it to one of our storefront accounts or sending a free demo link turns it on for everyone.
